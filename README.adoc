= THM Mail Support Application
:toc:
:toclevels: 3

== Purpose and current scope

This repository contains a university project for a shared email-support application. Registered internal users can work with mails through an Angular client and a Spring Boot API. PostgreSQL stores business data and SeaweedFS provides S3-compatible attachment storage. SMTP and IMAP connect the application to the configurable support mailbox.

The current implementation includes the reproducible one-command build/start workflow, Keycloak/OpenID Connect, the shared support-reply flow, the final flag-based IMAP strategy and the security infrastructure required by the assignment. Linting, dependency maintenance and C4 documentation remain tracked in `PROJEKTPLAN.md`; C4 is intentionally handled separately.

== Technology stack

* Angular, TypeScript, PrimeNG and Tailwind CSS
* Kotlin, Spring Boot, Spring Security and Spring Data JPA
* Gradle monorepo with a downloaded Node.js/npm toolchain
* Keycloak and OpenID Connect
* PostgreSQL
* SeaweedFS with its S3-compatible API
* Caddy, ModSecurity with OWASP CRS, Snort and Docker Compose
* H2 for backend tests and Vitest through Angular for frontend tests

== Authentication and authorization

Keycloak is the only identity provider. Docker Compose imports the `mail-system` realm, the public `mail-system-frontend` client and five development users from `keycloak/mail-system-realm.json`.

The Angular client uses the official Keycloak JavaScript adapter and Authorization Code Flow with PKCE `S256`. Tokens stay in the adapter's in-memory state and are refreshed before protected API calls. The Spring Boot backend is a stateless OAuth2 resource server and validates the token signature, expiration and issuer using the configured realm and JWK set.

Local business profiles contain no password. They are linked to Keycloak through the stable OIDC `sub` claim. Local login, registration, password encoding, an application-specific JWT service and a parallel LDAP integration are not used.

== Production-style container build and start

=== Prerequisites

* Docker with Docker Compose
* JDK 25 (the backend's configured Gradle toolchain)

No global Gradle, Node.js, npm, PostgreSQL or Keycloak installation is required.

=== Configuration

All Compose settings have usable local defaults. Copy `.env.example` to `.env` only when values must be overridden, especially for SMTP and IMAP. `.env` and real credentials must not be committed.

=== One command

On Windows:

[source,powershell]
----
.\gradlew.bat composeUp
----

On Linux or macOS:

[source,bash]
----
./gradlew composeUp
----

The task installs locked frontend dependencies with `npm ci`, runs backend and frontend tests, creates the Angular production output, builds the container images and starts the complete Compose stack. The application is available at https://localhost. The supplied development certificate is intentionally self-signed and must be accepted once in the browser. Requests to http://localhost are redirected to HTTPS.

Stop all services without deleting persistent data:

[source,powershell]
----
.\gradlew.bat composeDown
----

== Development build

Run the backend tests, frontend tests and frontend production build without starting containers:

[source,powershell]
----
.\gradlew.bat :backend:test :frontend:test :frontend:build
----

For Angular live development, first start the Compose stack, then run:

[source,bash]
----
cd frontend
npm ci
npm start
----

The configured Angular development proxy forwards `/api`, `/auth`, `/v3/api-docs` and `/swagger-ui` to https://localhost and accepts the local self-signed certificate. The development UI is available at http://localhost:4200.

== Runtime services

[cols="2,4",options="header"]
|===
|Service |Responsibility
|`ips` |Snort inline NFQUEUE demonstrator and the only published host ports, 80 and 443
|`proxy` |ModSecurity with OWASP CRS, HTTP-to-HTTPS redirect, TLS termination and reverse proxy
|`frontend` |Non-root Caddy process serving only Angular static files on the internal web network
|`backend` |REST API, business logic, SMTP/IMAP and S3 access
|`keycloak` |OIDC realm, login and access tokens
|`database` |PostgreSQL persistence
|`seaweedfs` |S3-compatible attachment storage
|===

Traffic follows `browser -> ips -> proxy`. The proxy routes `/auth/*` to Keycloak, `/api/*`, `/v3/api-docs*` and `/swagger-ui*` to the backend, and `/` to the static frontend. No application or data service is directly published to the host.

== Security infrastructure

Five Compose networks implement the small, explicit separation expected by the lecture exercise:

* `ingress`: Snort and the WAF
* `web`: WAF and static frontend
* `application`: WAF, backend and Keycloak
* `database`: backend and PostgreSQL
* `storage`: backend and SeaweedFS

All services use `no-new-privileges` and drop all Linux capabilities before adding back only those verified as necessary. Read-only root filesystems, non-root users and bounded `tmpfs` mounts are applied where the concrete images support them. Keycloak remains writable because its course-approved `start-dev` command writes below `/opt/keycloak/lib`; the ModSecurity image generates runtime configuration; PostgreSQL requires its data volume and five initialization/runtime capabilities; Snort runs as root with the five capabilities needed for iptables/NFQUEUE and a writable generated configuration. SeaweedFS persists only `/data` and otherwise runs read-only as UID 1000.

The WAF keeps OWASP CRS active at blocking paranoia level 2 and detection level 3. Narrow target exclusions cover only Keycloak's validated redirect/token syntax and the binary/JSON parts of the mail multipart endpoints. A SQL-injection probe remains blocked. Full rationale and the verified public-path behavior are documented in `SECURITY.md` and `VERIFICATION_CHECKLIST.md`.

== Configuration groups

The complete list with safe local defaults is maintained in `.env.example`.

* `DB_*`: PostgreSQL database, username, password and schema behavior
* `KEYCLOAK_*`, `OIDC_*`: development administrator, public URL, issuer, JWK set and discovery URL
* `APP_CORS_ALLOWED_ORIGINS`: explicit local browser origins
* `STORAGE_S3_*`: SeaweedFS endpoint, bucket, region and credentials
* `ATTACHMENT_MAX_FILE_SIZE`, `ATTACHMENT_MAX_REQUEST_SIZE`: shared HTTP/IMAP attachment limits
* `SPRING_MAIL_*`, `MAIL_FROM_ADDRESS`: SMTP settings
* `MAIL_IMAP_*`: IMAP settings and polling behavior

SMTP and IMAP are disabled when the corresponding required host or credentials are empty, so the example application remains directly usable without real THM secrets.

== Shared support workflow

Every registered Keycloak user can open the seeded or IMAP-imported external support mails. The reply action creates a draft addressed to the original external sender. It assigns or reuses a random `TICKET-XXXXXXXX` code and displays it in the prefixed reply subject before sending.

The authenticated user is stored as the internal author of the reply. The SMTP `From` header always uses the shared THM address configured as `MAIL_FROM_ADDRESS`; no user-selectable `Reply-To` recipient exists. Without a separate `Reply-To` header, subsequent external answers return to that same THM address.

The IMAP poller searches only messages without the `SEEN` flag. It marks a message as seen only after its database data and SeaweedFS attachments have been stored successfully. Failed imports remain unseen for the next poll, while the external `Message-ID` provides an additional deduplication guard.

Attachment validation is shared by HTTP uploads and IMAP imports. Normalized file names and MIME metadata are stored, while the internal SeaweedFS object key remains server-side. Authorized downloads are forced through `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`. The authenticated preview mode is restricted to JPEG, PNG, GIF and WebP; HTML, SVG and unknown formats are never served inline. Existing draft attachments are retained by identifier instead of being downloaded and uploaded again during an edit.

== OpenAPI

The backend generates the current OpenAPI 3.1 description from code and annotations at startup. Its global security declaration references the Keycloak OpenID Connect discovery endpoint. All operations have stable operation IDs, functional tags, summaries, descriptions, success/error responses and documented payload schemas including required properties. Error responses consistently reference the documented `AppError` body.

* Swagger UI: https://localhost/swagger-ui/index.html
* JSON: https://localhost/v3/api-docs
* YAML: https://localhost/v3/api-docs.yaml

The documentation endpoints are public. Application endpoints below `/api/**` require a valid Keycloak access token.
